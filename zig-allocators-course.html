What is an Allocator?
Before we write a single line of Zig, we need to understand what problem allocators actually solve — and why most languages hide them from you.

In most languages you've probably used — Python, JavaScript, Go — memory management is invisible. You create a list, the runtime handles it. You create an object, garbage is collected eventually. You never think about where the data lives or how long it persists.

Zig makes this explicit. When you want memory that outlives the current scope or whose size you don't know at compile time, you must ask for it — from an allocator. An allocator is simply an object that knows how to hand out memory and take it back.

The key mental model

Think of an allocator like a memory bank. You walk in, say "I need 64 bytes," it gives you a pointer to 64 bytes and notes the loan. Later you hand the pointer back and say "I'm done," and it marks those bytes as available again.

  Your code                    Allocator
  ─────────                    ─────────
  alloc(64)    ──────────▶  finds 64 free bytes
               ◀──────────  returns *[64]u8 ptr
  
  [use ptr...]
  
  free(ptr)    ──────────▶  marks those 64 bytes free

What makes Zig interesting is that there is no single global allocator. In C, malloc always calls into the system heap. In Zig, the allocator is passed as a parameter, which means:

  • You can swap allocators without changing your data structures
  • You can use a fast arena for a request, then free everything at once
  • You can use a fixed buffer instead of the heap in embedded contexts
  • You can wrap any allocator to add logging, leak detection, or limits

Why does this matter to you right now?

You've been writing Zig for ~75 exercises. You've seen std.ArrayList, you may have seen std.mem.Allocator parameters — now you'll understand exactly what those mean and how to use them confidently.

How to use this course

CHAPTER I · SECTION 1
Stack Memory
The stack is Zig's default memory region — fast, automatic, and strictly scoped.

Every variable you've declared in a Zig function so far has lived on the stack. The stack is a region of memory managed automatically by the CPU as functions are called and returned.

How the stack works

When you call a function, the CPU advances a pointer called the stack pointer to carve out space for that function's local variables. When the function returns, the stack pointer moves back — instantly reclaiming all that space.

  call main()
  ┌──────────────────────────────┐  ◀ stack pointer (high addr)
  │   main: x: u32 = 5          │
  │   main: arr: [3]u8           │
  │                              │
  │   call foo()               │
  │   ┌──────────────────────┐   │
  │   │  foo: temp: i32 = 0  │   │  ◀ stack pointer moves here
  │   │  foo: buf: [64]u8    │   │
  │   └──────────────────────┘   │
  │   (foo returns, SP resets)   │
  │                              │
  └──────────────────────────────┘  ◀ stack grows downward

Key properties of the stack:

  • Size known at compile time — every variable's size must be known before the program runs
  • Lifetime tied to scope — a local variable ceases to exist when its function returns
  • Extremely fast — just a pointer increment/decrement, no bookkeeping
  • Limited in size — typically 1–8 MB; overflow causes a crash (stack overflow)

In Zig

fn example() void {
    var x: u32 = 42;           // stack-allocated
    var buf: [128]u8 = undefined; // stack-allocated
    var point = Point{ .x = 1, .y = 2 }; // stack-allocated
    // All of the above are freed automatically when example() returns
}

Notice there is no allocator involved here at all. The compiler knows the size of u32, [128]u8, and Point at compile time, so it can reserve exactly the right amount of stack space before the function even runs.

A common mistake
Returning a pointer to a stack variable is undefined behavior in Zig (and C). The pointer becomes dangling the moment the function returns. We'll cover this in detail in Chapter IV.
CHAPTER I · SECTION 2
Heap Memory
The heap is where dynamic, runtime-sized, long-lived allocations live.

The heap is a large region of memory managed at runtime. Unlike the stack, allocations here don't have to be a fixed size, and they can outlive the function that created them. The tradeoff: you manage it yourself.

  Virtual Address Space
  ┌─────────────────────────────┐  high addr
  │  Stack (grows down ↓)       │
  │  ...                        │
  │                             │
  │    [free space]             │
  │                             │
  │  ...                        │
  │  Heap (grows up ↑)          │
  │  ┌───┐ ┌─────┐ ┌──┐        │
  │  │ A │ │  B  │ │C │ ...    │
  │  └───┘ └─────┘ └──┘        │
  ├─────────────────────────────┤
  │  BSS / Data (globals)       │
  ├─────────────────────────────┤
  │  Text (code)                │
  └─────────────────────────────┘  low addr

Each block (A, B, C above) was requested at runtime via alloc. They can be different sizes, created in any order, and freed independently. The heap manager tracks which regions are free.

When do you need the heap?

  • The size of your data is not known until runtime (user input, file contents)
  • You need the data to outlive the function that created it
  • The data is too large for the stack (large arrays, trees, graphs)
  • You need a variable number of items (dynamic arrays, hash maps)

In Zig — the first taste

const std = @import("std");

pub fn main() !void {
    var gpa = std.heap.GeneralPurposeAllocator(.{}){};
    const allocator = gpa.allocator();

    // Allocate space for 10 u32s on the heap
    const nums = try allocator.alloc(u32, 10);
    defer allocator.free(nums);

    for (nums, 0..) |*n, i| n.* = @intCast(i * i);

    std.debug.print("nums[5] = {}\n", .{nums[5]});
}

Three things to notice:

  1. We create a concrete allocator (GeneralPurposeAllocator) and call .allocator() to get the generic std.mem.Allocator interface
  2. alloc(T, n) returns a []T slice — heap-backed, runtime-sized
  3. defer allocator.free(nums) ensures cleanup — the heap does not free itself

PropertyStackHeap

LifetimeCurrent scopeManual (until free)

CHAPTER I · SECTION 3
Why Manual Allocation?
Garbage collectors are convenient — but convenience has a cost.

You might be wondering: Go, Java, Python — all manage memory for you. Why would Zig make you do it manually? Let's be specific about what you're actually trading.

What a garbage collector does

A GC periodically scans the heap, finds unreachable objects, and frees them. From your perspective as a programmer, memory just… goes away when you're done with it. This is genuinely ergonomic.

But a GC requires:

  • A runtime — a background process/goroutine watching memory
  • Stop-the-world pauses (or concurrent marking, which is complex and has overhead) — your program may pause for milliseconds
  • Extra memory overhead — the GC needs headroom to avoid running constantly; Go recommends 2× your live heap size
  • Non-deterministic timing — you can't predict when memory is freed

What you get from manual allocation

  • Predictable performance — no pauses, no surprise GC cycles
  • Minimal overhead — you pay only for what you allocate
  • No runtime required — Zig can target bare metal, kernels, WebAssembly with no runtime
  • Control over allocator strategy — use an arena for a request, a pool for fixed-size objects, a stack allocator for temporary work

What Zig adds over C

C also has manual allocation, but via the global malloc/free. Zig improves on this in several ways:

  • Allocators are passed as parameters, not global — testable, swappable
  • The GeneralPurposeAllocator detects leaks and double-frees in debug mode
  • Zig's type system catches many common errors at compile time
  • No implicit hidden allocations — if a function allocates, it takes an allocator param
The Zig philosophy on allocation
Zig follows a design principle: if a function allocates, it must accept an allocator parameter. This means you can audit any function signature and know whether it will touch the heap. No hidden allocations.

CHAPTER II · SECTION 1
std.mem.Allocator
The interface that makes every concrete allocator interchangeable.

In Zig, std.mem.Allocator is an interface — specifically, a struct containing a pointer to the underlying allocator and a vtable (a set of function pointers). This is Zig's way of doing runtime polymorphism without inheritance.

The two-layer structure

You'll always see this pattern:

// 1. The CONCRETE allocator — owns the actual memory management logic
var gpa = std.heap.GeneralPurposeAllocator(.{}){};

// 2. The INTERFACE — a thin wrapper you pass around
const allocator: std.mem.Allocator = gpa.allocator();

The concrete allocator (GeneralPurposeAllocator, ArenaAllocator, etc.) is a struct that lives somewhere — usually on your stack or as a field in another struct. The allocator() method returns a std.mem.Allocator which is just a fat pointer: a pointer to the concrete allocator, plus a vtable of function pointers.

  std.mem.Allocator (on your stack, 16 bytes)
  ┌─────────────────────────────────┐
  │ ptr  ──────────────────────────▶│  GeneralPurposeAllocator instance
  │ vtable ────────────────────────▶│  { .alloc = gpa_alloc,
  └─────────────────────────────────┘    .resize = gpa_resize,
                                         .free = gpa_free }

This means any code that accepts std.mem.Allocator can work with any backing allocator — swap GPA for Arena or FixedBuffer and the code doesn't change at all.

What's on the vtable?

The vtable has three slots:

  • alloc — allocates a new region
  • resize — tries to resize an existing allocation in-place
  • free — releases a region

You rarely call these directly — you use the higher-level methods we'll cover next.

This is Zig's interface pattern
std.mem.Allocator is the canonical example of Zig interfaces. You'll see this same vtable pattern used elsewhere in the stdlib — std.io.Reader, std.io.Writer, etc. Learning allocators teaches you the pattern itself.
CHAPTER II · SECTION 2
alloc, free, create, destroy
The four core operations on std.mem.Allocator.

The std.mem.Allocator interface exposes several methods. Four are essential and you'll use them constantly.

alloc — allocate a slice

fn alloc(comptime T: type, n: usize) error{OutOfMemory}![]T

Allocates space for n items of type T. Returns a slice []T. The memory is not initialized — it contains garbage. Use @memset or std.mem.zeroes if you need zeroed memory.

const nums = try allocator.alloc(u32, 100);   // []u32, length 100
defer allocator.free(nums);
@memset(nums, 0);                              // zero it if needed

free — release a slice

fn free(memory: anytype) void

Releases memory previously returned by alloc. You must pass the exact same slice — same pointer, same length. Passing a sub-slice is undefined behavior.

create — allocate a single value

fn create(comptime T: type) error{OutOfMemory}!*T

Allocates space for a single value of type T. Returns a pointer *T. Think of it as alloc(T, 1) but returning a pointer instead of a slice.

const node = try allocator.create(Node);   // *Node
defer allocator.destroy(node);
node.* = Node{ .value = 42, .next = null };

destroy — release a single value

fn destroy(ptr: anytype) void

Releases memory returned by create. Pair exactly: alloc/free, create/destroy.

Also useful: dupe

const copy = try allocator.dupe(u8, original_slice);
defer allocator.free(copy);

dupe allocates a copy of an existing slice. Very common for strings.

Summary

MethodReturnsFree withUse for
alloc(T, n)[]TfreeArrays, slices
create(T)*TdestroySingle structs, nodes
dupe(T, slice)[]TfreeCopying slices
realloc(old, n)[]TfreeResizing (like C realloc)
Never mix the pairs
Freeing an alloc result with destroy, or a create result with free, is undefined behavior. In debug mode, the GPA will catch this.
CHAPTER II · SECTION 3
Passing Allocators Around
The convention that makes Zig code composable and testable.

The most important design principle in Zig's allocator system: functions that allocate take an allocator as a parameter. They never reach for a global allocator. This has profound consequences for how you structure programs.

The correct pattern

// CORRECT — caller decides the allocation strategy
fn buildMessage(allocator: std.mem.Allocator, name: []const u8) ![]u8 {
    return std.fmt.allocPrint(allocator, "Hello, {s}!", .{name});
}

// WRONG — hidden allocation, caller can't control strategy
var global_alloc = std.heap.page_allocator;
fn buildMessageBad(name: []const u8) ![]u8 {
    return std.fmt.allocPrint(global_alloc, "Hello, {s}!", .{name});
}

Why does this matter?

When the allocator is a parameter, the caller can choose:

// In tests: use a test allocator that detects leaks
const msg = try buildMessage(std.testing.allocator, "world");
defer std.testing.allocator.free(msg);

// In a web server: use an arena per-request, free everything at once
var arena = std.heap.ArenaAllocator.init(gpa.allocator());
defer arena.deinit();
const msg = try buildMessage(arena.allocator(), "world");
// no need to free msg individually — arena.deinit() handles it

Where in the parameter list?

By convention, allocator is the first parameter when it's needed:

fn parseJson(allocator: std.mem.Allocator, input: []const u8) !Value { ... }
fn readFile(allocator: std.mem.Allocator, path: []const u8) ![]u8 { ... }
fn cloneList(allocator: std.mem.Allocator, list: List) !List { ... }

Structs that need an allocator

When a struct needs to allocate, it stores the allocator as a field — not the concrete type, but the interface:

const MyBuffer = struct {
    allocator: std.mem.Allocator,
    data: []u8,

    pub fn init(allocator: std.mem.Allocator, size: usize) !MyBuffer {
        return .{
            .allocator = allocator,
            .data = try allocator.alloc(u8, size),
        };
    }

    pub fn deinit(self: MyBuffer) void {
        self.allocator.free(self.data);
    }
};
Reading stdlib signatures
Now when you see std.ArrayList(T).init(allocator) or std.StringHashMap(V).init(allocator), you know exactly what's happening: you're handing the data structure an allocator it will use for all internal allocations, and you're responsible for calling deinit() when done.

CHAPTER III · SECTION 1
GeneralPurposeAllocator
Your default allocator — safe, thorough, and full of debug features.

The std.heap.GeneralPurposeAllocator is the Swiss Army knife of Zig allocators. It's designed to be safe and informative in debug builds, and reasonably fast in release builds.

Creating and using it

var gpa = std.heap.GeneralPurposeAllocator(.{}){};
defer {
    const leaked = gpa.deinit();
    if (leaked == .leak) @panic("memory leak detected!");
}
const allocator = gpa.allocator();

The gpa.deinit() call at the end checks for leaks — all memory allocated via this GPA should have been freed before deinit. It returns a Check enum (.ok or .leak).

Debug features

In debug builds, GPA performs:

  • Leak detection — reports any allocations not freed by deinit()
  • Double-free detection — panics if you free the same memory twice
  • Use-after-free detection — fills freed memory with a sentinel byte (0xaa), so reading freed memory gives obviously bad values
  • Allocation metadata tracking — tracks the stack trace of every allocation for reporting

Configuration options

The (.{}) is a comptime config struct. You can customize behavior:

var gpa = std.heap.GeneralPurposeAllocator(.{
    .safety = true,           // enable safety checks (default in debug)
    .thread_safe = false,    // disable mutex if single-threaded
    .retain_metadata = true, // keep freed metadata for better diagnostics
}){};

When to use GPA

  • General-purpose heap allocation in applications
  • Any context where you want leak detection
  • Development and testing — the debug safety is invaluable
GPA lives on the stack — be careful
var gpa = ... puts the GPA struct on the stack of the current function. Don't let it go out of scope while allocations from it are still alive. In practice, put it at the top of main().
CHAPTER III · SECTION 2
ArenaAllocator
Allocate freely, free everything at once. The workhorse of request-scoped memory.

The ArenaAllocator is one of the most important allocators in practice. The idea is beautifully simple: individual frees do nothing; arena.deinit() frees everything at once.

  Arena memory pool:
  ┌────────────────────────────────────────────────┐
  │  alloc A (24B) │ alloc B (8B) │ alloc C (100B) │ free ──▶
  └────────────────────────────────────────────────┘
                                        ↑
                              bump pointer moves right
                              
  arena.deinit() ──▶ entire pool freed at once

Internally, the arena keeps a linked list of large memory chunks. Each alloc just bumps a pointer forward — no bookkeeping per allocation. This makes allocation essentially free (a pointer increment).

Setup and usage

var arena = std.heap.ArenaAllocator.init(gpa.allocator());
defer arena.deinit();

const allocator = arena.allocator();

// Allocate freely — no need to free individually
const a = try allocator.alloc(u8, 100);
const b = try allocator.create(Node);
const c = try std.fmt.allocPrint(allocator, "hello {}", .{42});

// free(a), free(c), destroy(b) all do nothing for arenas
// arena.deinit() frees the underlying backing allocator chunks

The backing allocator

An arena doesn't own raw memory — it wraps another allocator that it uses to request large chunks. You pass a backing allocator to init(). Typically this is your GPA:

var gpa = std.heap.GeneralPurposeAllocator(.{}){};
defer _ = gpa.deinit();

var arena = std.heap.ArenaAllocator.init(gpa.allocator());
defer arena.deinit();

When to use ArenaAllocator

  • Request handling — web server handles a request, allocates many small things, frees it all when the response is sent
  • Parsing — build a parse tree, use it, discard the whole thing
  • Batch processing — process a batch of data, arena holds all intermediate state, deinit when batch is done
  • Tests — use an arena in test setup, deinit at end

reset() — reuse without deallocation

// Process multiple requests reusing the same arena backing memory
for (requests) |req| {
    defer _ = arena.reset(.retain_capacity);
    const response = try handleRequest(arena.allocator(), req);
    try sendResponse(response);
}

reset(.retain_capacity) frees all objects but keeps the backing chunk allocated, so the next batch doesn't need to ask the OS for memory again. Very efficient for repeated fixed-ish workloads.

CHAPTER III · SECTION 3
FixedBufferAllocator
Heap allocation from a stack buffer. No OS calls, no failures (until full).

The FixedBufferAllocator treats a fixed byte array as its memory pool. You hand it a []u8 buffer, and it parcels out pieces of it on demand. No OS interaction whatsoever.

var buffer: [4096]u8 = undefined;
var fba = std.heap.FixedBufferAllocator.init(&buffer);
const allocator = fba.allocator();

const nums = try allocator.alloc(u32, 10); // carved from buffer
const s = try allocator.alloc(u8, 100);  // carved from buffer
// If you exceed 4096 bytes total: error.OutOfMemory

How it works internally

  buffer[0..4096]:
  ┌──────────────────────────────────────────────────────┐
  │ nums (40B)  │  s (100B)  │  ...(future)  │  free space  │
  └──────────────────────────────────────────────────────┘
                              ↑
                        end_index

The FBA simply keeps an end_index into the buffer. Each allocation advances it. Free operations don't do anything (like an arena) — unless the freed allocation was the last one, in which case end_index moves back (it's a stack allocator at heart).

When to use FixedBufferAllocator

  • Embedded/no-heap contexts — microcontrollers with no dynamic memory
  • No-failure paths — where you know your upper bound and can pre-allocate
  • Performance-critical hot paths — zero OS involvement, often in L1 cache
  • Stack-backed scratch space — allocate from the stack for small temporary work

Combining FBA with a fallback

A common pattern: try the fixed buffer first, fall back to heap on overflow. Zig has StackFallbackAllocator for exactly this (next section).

Buffer lifetime
The buffer must outlive all allocations from the FBA. Since the buffer is usually stack-allocated (var buffer: [N]u8), this means the FBA should not outlive the function that owns the buffer.
CHAPTER III · SECTION 4
C Allocator & Page Allocator
The low-level primitives underlying most allocators.

std.heap.c_allocator

This is just a thin wrapper around C's malloc/free. It's available when linking libc.

const allocator = std.heap.c_allocator;
const buf = try allocator.alloc(u8, 256);
defer allocator.free(buf);

When to use it: when you're linking libc anyway and want maximum compatibility with C libraries that hand you malloc-allocated memory. Has no safety checks.

std.heap.page_allocator

Goes directly to the OS via mmap/VirtualAlloc. Allocates whole memory pages (typically 4096 bytes). No overhead, no bookkeeping — but every allocation is at least one page.

const allocator = std.heap.page_allocator;
const big_buf = try allocator.alloc(u8, 1024 * 1024); // 1 MB
defer allocator.free(big_buf);

When to use it: as a backing allocator for arenas or GPA, not for small allocations. Allocating a single u32 wastes 4092 bytes of a page.

The typical production stack

// page_allocator provides raw OS pages
// GPA manages sub-page allocations on top of that
// ArenaAllocator provides fast bump allocation backed by GPA

var gpa = std.heap.GeneralPurposeAllocator(.{}){};
defer _ = gpa.deinit();  // GPA uses page_allocator internally by default

var arena = std.heap.ArenaAllocator.init(gpa.allocator());
defer arena.deinit();

CHAPTER III · SECTION 5
StackFallbackAllocator
Try the stack buffer first; fall back to heap on overflow.

std.heap.stackFallback(N, fallback) creates a combined allocator that tries a fixed N-byte stack buffer first, and only falls back to the given allocator when that runs out.

var sfb = std.heap.stackFallback(1024, gpa.allocator());
const allocator = sfb.get();

// Small allocation — served from the stack buffer, zero heap involvement
const small = try allocator.alloc(u8, 100);

// Large allocation — overflows to GPA
const large = try allocator.alloc(u8, 2000);

defer allocator.free(small);
defer allocator.free(large);

Why this is powerful

Many operations involve small amounts of data in the common case but occasionally need more. A path manipulation function, a small JSON serializer, a URL builder. With StackFallbackAllocator, the common case never touches the heap, making it fast and allocation-failure-resistant. Only the unusual large case pays the heap cost.

std.ArrayList uses this internally
std.ArrayListUnmanaged starts with a small inline buffer and grows to the heap. The same pattern. Now you know how it works.

CHAPTER IV · SECTION 1
Leaks & GPA Detection
Forgetting to free — and how Zig catches it.

A memory leak occurs when you allocate memory but never free it. The allocation is no longer reachable (the pointer was lost) but the allocator still thinks it's in use. Over time, leaks cause programs to consume ever-increasing memory until the OS kills them.

A classic leak

pub fn main() !void {
    var gpa = std.heap.GeneralPurposeAllocator(.{}){};
    defer _ = gpa.deinit();
    const allocator = gpa.allocator();

    const buf = try allocator.alloc(u8, 64);
    // LEAK: buf is never freed!
    _ = buf;
}

When you run this, GPA's deinit() will print something like:

error(gpa): memory address 0x... leaked:
/path/to/file.zig:7:45: 0x... in main (file)
    const buf = try allocator.alloc(u8, 64);

It shows you exactly where the allocation was made — the full stack trace. This is why GPA is invaluable during development.

Using defer to prevent leaks

The idiomatic Zig pattern is to pair each allocation with a defer immediately:

const buf = try allocator.alloc(u8, 64);
defer allocator.free(buf);  // immediately after — never forget to add this

// ... use buf ...

Writing defer free right after alloc ensures the free happens at the end of the current scope even if an error is returned partway through.

Leak detection in tests

test "no leaks" {
    const allocator = std.testing.allocator;
    // std.testing.allocator is a GPA that fails the test on leaks
    
    const data = try allocator.alloc(u32, 10);
    defer allocator.free(data);
    
    // If free is missing, the test fails with a leak report
}

std.testing.allocator is a GPA configured to fail tests on leaks. Always use it in tests — it makes memory bugs obvious immediately.

CHAPTER IV · SECTION 2
Use-after-free
Reading memory you've already returned — undefined behavior with no guarantees.

A use-after-free happens when you hold a pointer to memory, free it, and then try to read or write through that pointer. The memory may have been reallocated to something else, zeroed, or left as garbage.

const buf = try allocator.alloc(u8, 8);
buf[0] = 42;
allocator.free(buf);

// USE-AFTER-FREE — undefined behavior
std.debug.print("val: {}\n", .{buf[0]}); // could print 0xaa, crash, or 42 by luck

How GPA catches it

In debug mode, GPA fills freed memory with the sentinel byte 0xaa. If you read a freed buffer and see values like 170 (0xaa) or addresses like 0xaaaa...aaaa, that's the UAF sentinel. GPA will also panic on double-free (next section) when it detects you're freeing memory that's already been marked freed.

Why it's dangerous

In release builds there are no checks. The memory may have been reused for a completely different allocation. You might:

  • Silently corrupt data in an unrelated part of the program
  • Create a security vulnerability (use-after-free is a common exploit vector)
  • Get a segfault — or worse, get the wrong answer silently

Prevention patterns

// Pattern 1: null out the pointer after freeing (convention, not enforced)
allocator.free(buf);
buf = undefined; // marks it as unusable — UB to read in debug mode

// Pattern 2: use defer so the free is the LAST thing that can happen
const buf = try allocator.alloc(u8, 8);
defer allocator.free(buf);
// Can't use buf after the deferred free because we're past the scope
undefined is your friend here
In Zig, assigning undefined to a variable doesn't zero it — in debug builds it fills with 0xaa. Reading undefined memory is itself undefined behavior in safe builds, so Zig will panic if you try. This is intentionally useful for catching bugs.
CHAPTER IV · SECTION 3
Double-free
Freeing the same allocation twice — corrupting the allocator's state.

A double-free is freeing the same pointer twice. This corrupts the allocator's internal bookkeeping, leading to bizarre bugs or crashes.

const buf = try allocator.alloc(u8, 64);
allocator.free(buf);
allocator.free(buf); // DOUBLE-FREE — GPA panics in debug mode

A subtle source of double-frees

Double-frees often appear in error handling paths or when ownership is unclear:

fn processData(allocator: std.mem.Allocator) !void {
    const buf = try allocator.alloc(u8, 1024);
    defer allocator.free(buf);  // will free on both success AND error return

    const result = try transform(allocator, buf);
    // if transform takes ownership and frees buf itself,
    // the defer above is a double-free!
}

This is why clear ownership semantics matter — covered in Chapter V.

What GPA does

In debug mode, GPA tracks a "free list" of previously freed allocations. When you call free, it checks whether the address has already been freed. If so: panic with a clear message.

The rule of one owner
Every allocation should have exactly one owner — the entity responsible for freeing it. Document this in function signatures and comments. "Caller owns the returned slice" is standard Zig documentation phrasing.
CHAPTER IV · SECTION 4
Dangling Pointers
Pointers that outlive what they point to.

A dangling pointer points to memory that is no longer valid — either freed heap memory (use-after-free) or stack memory that has gone out of scope.

Returning a stack address — the classic bug

fn getPtr() *u32 {
    var x: u32 = 42;
    return &x; // DANGLING — x dies when getPtr() returns
}

pub fn main() void {
    const p = getPtr();
    // p points to memory on getPtr()'s stack frame, which is now gone
    std.debug.print("val: {}\n", .{p.*}); // undefined behavior
}

Zig does not prevent this at compile time (it's a hard problem in general). But in ReleaseSafe and Debug builds, Zig's safety checks may catch obvious violations.

Slices into freed memory

var list = std.ArrayList(u8).init(allocator);
defer list.deinit();

try list.appendSlice("hello");
const slice = list.items; // points into ArrayList's internal buffer

try list.appendSlice(" world and more text that forces reallocation");
// ArrayList may have reallocated its buffer! slice is now dangling.
std.debug.print("{s}\n", .{slice}); // potential dangling pointer

This is a subtle but common source of bugs when working with growing collections — if the collection reallocates, all existing slices into it become invalid.

Safe alternatives

  • Store indices instead of pointers into collections
  • Do all operations, then take a slice reference
  • Use list.ensureTotalCapacity(n) to pre-allocate and prevent reallocation

CHAPTER V · SECTION 1
Who Owns the Allocation?
Ownership is a contract. Zig doesn't enforce it — you document and honor it.

Every heap allocation has an owner — an entity responsible for eventually calling free. In Zig, unlike Rust, ownership is not enforced by the compiler. It's a convention you express through documentation and code structure.

Three ownership models

1. Caller allocates, caller frees (most common)

/// Fills buf with data. Caller is responsible for providing
/// and managing buf.
fn fillBuffer(buf: []u8) void {
    @memset(buf, 0xAB);
}

2. Callee allocates, caller frees (documented)

/// Returns a newly allocated string. Caller owns the result
/// and must free it with the same allocator.
fn buildString(allocator: std.mem.Allocator) ![]u8 {
    return allocator.dupe(u8, "hello");
}

// usage:
const s = try buildString(allocator);
defer allocator.free(s); // caller's responsibility

3. Struct takes ownership (stored internally)

/// Takes ownership of `data`. Do not free `data` yourself after
/// passing it here — Buffer.deinit() will free it.
fn Buffer.fromOwnedSlice(allocator: std.mem.Allocator, data: []u8) Buffer {
    return .{ .allocator = allocator, .data = data };
}

Documenting ownership in Zig

The Zig stdlib uses consistent phrasing — you should too:

  • "Caller owns the returned memory" — function allocates, caller frees
  • "Takes ownership of X" — struct/function will free X; caller must not
  • "Borrows X" — function uses X but doesn't free it
When ownership is unclear, bugs appear
Most double-frees and leaks in Zig code come from ambiguous ownership. If you can't immediately say "this allocation is freed by X," that's a design smell.
CHAPTER V · SECTION 2
init / deinit Pattern
The idiomatic Zig lifecycle for structs that own memory.

In Zig, the conventional way to handle a struct that needs to allocate is the init/deinit pattern. It's analogous to constructors/destructors but explicit.

const Cache = struct {
    allocator: std.mem.Allocator,
    entries: std.StringHashMap([]const u8),

    /// Create a new Cache. Caller must call deinit() when done.
    pub fn init(allocator: std.mem.Allocator) Cache {
        return .{
            .allocator = allocator,
            .entries = std.StringHashMap([]const u8).init(allocator),
        };
    }

    /// Free all resources owned by this Cache.
    pub fn deinit(self: *Cache) void {
        // Free all values in the map
        var it = self.entries.valueIterator();
        while (it.next()) |v| self.allocator.free(v.*);
        self.entries.deinit();
    }

    pub fn put(self: *Cache, key: []const u8, value: []const u8) !void {
        const owned_value = try self.allocator.dupe(u8, value);
        try self.entries.put(key, owned_value);
    }
};

// Usage
var cache = Cache.init(allocator);
defer cache.deinit();

try cache.put("key", "value");

Key rules of init/deinit

  • init takes an allocator (if needed), returns the struct by value
  • deinit takes self: *MyStruct (a pointer, so it can mutate) and frees everything
  • The caller immediately follows init with defer deinit()
  • deinit may be called on zero-initialized or partially-initialized structs (be defensive)
You've seen this in the stdlib
std.ArrayList.init(allocator) / list.deinit(). std.StringHashMap.init(allocator) / map.deinit(). Now you know exactly what they're doing — and you can build your own types that follow the same contract.
CHAPTER V · SECTION 3
Returning Allocated Memory
Transferring ownership through return values.

Sometimes a function's job is to produce a newly allocated value. Ownership transfers to the caller. This is fine — as long as it's documented.

The error path problem

When a function allocates multiple things and one fails, you must clean up the successful allocations:

fn buildPair(allocator: std.mem.Allocator) !struct { a: []u8, b: []u8 } {
    const a = try allocator.alloc(u8, 64);
    // If the next line fails, 'a' leaks!
    const b = try allocator.alloc(u8, 64);
    return .{ .a = a, .b = b };
}

Fix: use errdefer on earlier allocations:

fn buildPair(allocator: std.mem.Allocator) !struct { a: []u8, b: []u8 } {
    const a = try allocator.alloc(u8, 64);
    errdefer allocator.free(a); // free 'a' if we return an error

    const b = try allocator.alloc(u8, 64);
    // If we reach here, both succeeded
    return .{ .a = a, .b = b };
    // errdefer for 'a' does NOT run on success — that's the point
}

errdefer — the essential tool

errdefer is like defer but it only runs when the function returns an error. On a successful return, errdefer is skipped. This makes it perfect for cleanup in the "something went wrong partway" path.

fn complexInit(allocator: std.mem.Allocator) !MyStruct {
    var result = MyStruct{};

    result.buf_a = try allocator.alloc(u8, 100);
    errdefer allocator.free(result.buf_a);

    result.buf_b = try allocator.alloc(u8, 200);
    errdefer allocator.free(result.buf_b);

    result.map = std.StringHashMap(u32).init(allocator);
    errdefer result.map.deinit();

    // ... more setup that might fail ...

    return result; // all errdefers skipped — caller owns result
}
The errdefer pattern is mandatory for multi-allocation functions
Every time you have two or more allocations in a function that returns the allocated memory to the caller, you need errdefer on all but the last allocation. This is one of the most important patterns in safe Zig.
CHAPTER V · SECTION 4
Allocators in Structs
Storing the allocator so the struct can manage its own memory.

When a struct needs to allocate and deallocate memory throughout its lifetime (not just at init), it stores the allocator as a field. This is the pattern used by ArrayList, HashMap, and virtually every stdlib container.

const GrowableBuffer = struct {
    allocator: std.mem.Allocator,
    data: []u8,
    len: usize,

    pub fn init(allocator: std.mem.Allocator) GrowableBuffer {
        return .{
            .allocator = allocator,
            .data = &[0]u8{},
            .len = 0,
        };
    }

    pub fn deinit(self: *GrowableBuffer) void {
        if (self.data.len > 0)
            self.allocator.free(self.data);
    }

    pub fn append(self: *GrowableBuffer, byte: u8) !void {
        if (self.len == self.data.len) {
            const new_cap = if (self.data.len == 0) 8 else self.data.len * 2;
            self.data = try self.allocator.realloc(self.data, new_cap);
        }
        self.data[self.len] = byte;
        self.len += 1;
    }

    pub fn slice(self: GrowableBuffer) []u8 {
        return self.data[0..self.len];
    }
};

Why store the allocator, not pass it everywhere?

Methods like append may allocate. If the allocator weren't stored, every single method call would need the allocator as a parameter — verbose and error-prone. Storing it once in init keeps the API clean.

Never store a concrete allocator type

// WRONG — couples the struct to a specific allocator implementation
const BadStruct = struct {
    gpa: *std.heap.GeneralPurposeAllocator(.{}),
};

// CORRECT — works with any allocator
const GoodStruct = struct {
    allocator: std.mem.Allocator,
};

CHAPTER VI · SECTION 1
The Allocator VTable
How the interface works under the hood — and how to plug into it.

To build your own allocator, you need to understand how std.mem.Allocator achieves runtime polymorphism. The answer is a classic vtable — a struct of function pointers.

// Simplified view of std.mem.Allocator (actual stdlib source)
pub const Allocator = struct {
    ptr: *anyopaque,        // pointer to the concrete allocator
    vtable: *const VTable,  // function dispatch table

    pub const VTable = struct {
        alloc:  *const fn(ctx: *anyopaque, len: usize, ptr_align: u8,
                           ret_addr: usize) ?[*]u8,
        resize: *const fn(ctx: *anyopaque, buf: []u8, buf_align: u8,
                           new_len: usize, ret_addr: usize) bool,
        free:   *const fn(ctx: *anyopaque, buf: []u8, buf_align: u8,
                           ret_addr: usize) void,
    };
};

When you call allocator.alloc(u8, 100), the method call goes through vtable.alloc, passing ptr as the context. Each concrete allocator provides its own implementations of these three functions.

The allocator() method pattern

Each concrete allocator type has an allocator() method that packages self and its vtable into a std.mem.Allocator:

pub fn allocator(self: *MyAllocator) std.mem.Allocator {
    return .{
        .ptr = self,
        .vtable = &.{
            .alloc  = myAlloc,
            .resize = myResize,
            .free   = myFree,
        },
    };
}

fn myAlloc(ctx: *anyopaque, len: usize, ptr_align: u8, ret_addr: usize) ?[*]u8 {
    const self: *MyAllocator = @ptrCast(@alignCast(ctx));
    // ... implementation ...
}

The @ptrCast(@alignCast(ctx)) recovers the typed pointer from the *anyopaque. The vtable is a comptime constant — it's placed in the binary's read-only data segment.

This pattern is used throughout Zig
std.io.Reader, std.io.Writer, std.io.SeekableStream all use the same vtable pattern. Understand it once, and you understand Zig's runtime polymorphism system completely.
CHAPTER VI · SECTION 2
A Counting Allocator
Wrap any allocator to track total bytes allocated.

A counting allocator wraps another allocator (the "backing" allocator) and tracks how many bytes have been allocated and freed. Every real allocation is delegated to the backing allocator — the wrapper just observes and counts.

const CountingAllocator = struct {
    backing: std.mem.Allocator,
    total_allocated: usize = 0,
    total_freed: usize = 0,

    pub fn init(backing: std.mem.Allocator) CountingAllocator {
        return .{ .backing = backing };
    }

    pub fn allocator(self: *CountingAllocator) std.mem.Allocator {
        return .{
            .ptr = self,
            .vtable = &.{
                .alloc  = alloc,
                .resize = resize,
                .free   = free,
            },
        };
    }

    fn alloc(ctx: *anyopaque, len: usize, ptr_align: u8, ret_addr: usize) ?[*]u8 {
        const self: *CountingAllocator = @ptrCast(@alignCast(ctx));
        const result = self.backing.vtable.alloc(self.backing.ptr, len, ptr_align, ret_addr);
        if (result != null) self.total_allocated += len;
        return result;
    }

    fn resize(ctx: *anyopaque, buf: []u8, buf_align: u8, new_len: usize, ret_addr: usize) bool {
        const self: *CountingAllocator = @ptrCast(@alignCast(ctx));
        return self.backing.vtable.resize(self.backing.ptr, buf, buf_align, new_len, ret_addr);
    }

    fn free(ctx: *anyopaque, buf: []u8, buf_align: u8, ret_addr: usize) void {
        const self: *CountingAllocator = @ptrCast(@alignCast(ctx));
        self.total_freed += buf.len;
        self.backing.vtable.free(self.backing.ptr, buf, buf_align, ret_addr);
    }

    pub fn currentUsage(self: CountingAllocator) usize {
        return self.total_allocated - self.total_freed;
    }
};

Usage

var counter = CountingAllocator.init(gpa.allocator());
const allocator = counter.allocator();

const buf = try allocator.alloc(u8, 100);
std.debug.print("using {} bytes\n", .{counter.currentUsage()}); // 100
allocator.free(buf);
std.debug.print("using {} bytes\n", .{counter.currentUsage()}); // 0

This pattern — wrapping an allocator to add behavior — is one of the most powerful tools in Zig. You can add logging, limits, profiling, or any behavior you want, with zero changes to your existing code.

CHAPTER VI · SECTION 3
A Logging Allocator
Print every allocation and free — useful for debugging allocation patterns.

Building on the counting allocator pattern, a logging allocator prints each allocation and free to stderr. Zig actually ships one: std.heap.LoggingAllocator. But building it yourself cements the vtable pattern.

const LoggingAllocator = struct {
    backing: std.mem.Allocator,

    pub fn allocator(self: *LoggingAllocator) std.mem.Allocator {
        return .{ .ptr = self, .vtable = &.{
            .alloc = alloc, .resize = resize, .free = free,
        }};
    }

    fn alloc(ctx: *anyopaque, len: usize, ptr_align: u8, ret_addr: usize) ?[*]u8 {
        const self: *LoggingAllocator = @ptrCast(@alignCast(ctx));
        const result = self.backing.vtable.alloc(self.backing.ptr, len, ptr_align, ret_addr);
        if (result) |ptr| {
            std.debug.print("[alloc] {} bytes at 0x{x}\n", .{len, @intFromPtr(ptr)});
        } else {
            std.debug.print("[alloc] FAILED {} bytes\n", .{len});
        }
        return result;
    }

    fn resize(ctx: *anyopaque, buf: []u8, buf_align: u8, new_len: usize, ret_addr: usize) bool {
        const self: *LoggingAllocator = @ptrCast(@alignCast(ctx));
        const ok = self.backing.vtable.resize(self.backing.ptr, buf, buf_align, new_len, ret_addr);
        std.debug.print("[resize] 0x{x}: {} -> {} ({})\n",
            .{@intFromPtr(buf.ptr), buf.len, new_len, if (ok) "ok" else "fail"});
        return ok;
    }

    fn free(ctx: *anyopaque, buf: []u8, buf_align: u8, ret_addr: usize) void {
        const self: *LoggingAllocator = @ptrCast(@alignCast(ctx));
        std.debug.print("[free]  {} bytes at 0x{x}\n", .{buf.len, @intFromPtr(buf.ptr)});
        self.backing.vtable.free(self.backing.ptr, buf, buf_align, ret_addr);
    }
};

Chaining allocators

You can chain these wrappers:

// page_allocator → GPA (sub-page management) → Logger → Counter → your code
var gpa = std.heap.GeneralPurposeAllocator(.{}){};
var logger = LoggingAllocator{ .backing = gpa.allocator() };
var counter = CountingAllocator.init(logger.allocator());
const allocator = counter.allocator();
CHAPTER VI · SECTION 4
A Pool Allocator
Fixed-size allocations at maximum speed — the foundation of game engines and servers.

A pool allocator is specialized for allocating many objects of the same size. Instead of general heap management overhead per object, it pre-allocates a large block and maintains a free list of same-sized slots. Alloc and free are O(1) with zero fragmentation.

  Pool: 8 slots of sizeof(Node)
  ┌────┬────┬────┬────┬────┬────┬────┬────┐
  │ A  │ B  │ -- │ C  │ -- │ -- │ D  │ -- │
  └────┴────┴────┴────┴────┴────┴────┴────┘
  used: A,B,C,D    free list: slots 2,4,5,7
  
  alloc() → pop slot 2 from free list, return ptr
  free(C) → push slot 3 onto free list

Zig's stdlib has std.heap.MemoryPool(T) for exactly this:

const NodePool = std.heap.MemoryPool(Node);

var pool = NodePool.init(gpa.allocator());
defer pool.deinit();

// Very fast — no general heap lookup, just free list pop
const n1 = try pool.create();
const n2 = try pool.create();
n1.* = Node{ .value = 1, .next = n2 };
n2.* = Node{ .value = 2, .next = null };

pool.destroy(n1);  // free list push — instant
pool.destroy(n2);

When to use a pool allocator

  • Game entities — thousands of same-sized objects created and destroyed per frame
  • Network connections — each connection is the same struct size
  • Parse tree nodes — all nodes are the same union type
  • Anywhere you have many allocations and frees of the same type

Memory layout advantage

Pool-allocated objects of the same type are in contiguous memory. This dramatically improves CPU cache performance — iterating pool objects is cache-friendly, unlike general heap allocations which may be scattered.

EPILOGUE
Choosing the Right Allocator
A practical decision guide for real Zig programs.

You've now covered the full allocator landscape. Here's a condensed decision guide for production code.

The Decision Tree

  Do you know the max size at compile time
  AND it's small enough for the stack?
  ├── YES → Stack variable. No allocator needed.
  └── NO ↓

  Will all allocations be freed together
  at the end of a logical unit (request, operation)?
  ├── YES → ArenaAllocator. Fast, simple, no individual frees.
  └── NO ↓

  Do you need a fixed upper bound and no heap?
  (embedded, no-OS, ultra-low latency)
  ├── YES → FixedBufferAllocator.
  └── NO ↓

  Are you allocating many same-sized objects?
  ├── YES → std.heap.MemoryPool(T) (pool allocator).
  └── NO ↓

  General use → GeneralPurposeAllocator
  (GPA in debug, consider c_allocator in release if perf critical)

The golden rules

  1. Functions that allocate take an allocator parameter. No hidden global allocations.
  2. Every allocation has exactly one owner. Document it. Honor it.
  3. Pair alloc with defer free immediately. Never let them drift apart in the source.
  4. Use errdefer for multi-allocation functions that return the memory to the caller.
  5. Use std.testing.allocator in all tests. It makes leaks into test failures.
  6. Start with GPA in development. Its debug checks will catch most bugs early.
